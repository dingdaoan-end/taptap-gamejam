# 《夜之乐章》项目检索总结

检索日期：2026-10-09。依据当前工作区代码、场景、工程配置、README、设计文档与测试源码重新整理。本次未修改玩法或工程配置，未启动编辑器或生成试玩包。

## 1. 项目定位与当前阶段

这是以“涌现”为主题的钢琴塔防灰盒原型：玩家通过塔位和音高筛选改变击杀顺序，击杀产生音符，音符组成旋律并反过来奖励防守。

当前已具备“准备布阵 → 节拍守夜 → 乐句奖励 → 胜负结算 → 击杀回放”的完整单夜循环。适合验证核心玩法和听感，距离设计文档里的多夜、白天采风、多乐器与 Boss 完整体验仍有明显差距。当前没有传统音游的按键判定线。

## 2. 当前实际规则

| 项目 | 代码中的实现 |
| --- | --- |
| 战场 | 12×7 网格，通道位于 y=1、3、5；两端列不能建塔 |
| 节奏 | 110 BPM，每拍约 0.545 秒；每 16 拍结算乐句 |
| 初始资源 | 据点 10 HP、24 币；示例布局消耗全部初始币，放置三座塔 |
| 琴塔 | 8 币，上限 8 座；每拍单体攻击，曼哈顿射程 3，命中即击杀 |
| 索敌 | 按塔的列表顺序执行；优先攻击离左端据点最近的合格敌人，同列按敌人 ID 决定 |
| 筛选 | 全部、独奏指定音高、跳过指定音高；筛选音高不会改变被杀敌人的发声音高 |
| 敌人 | 普通怪每拍 1 格，装饰音怪每拍 2 格；装饰音怪只经过偶数列 |
| 波次 | 三波，共 44 个敌人，其中 5 个装饰音怪；出生区间分别为拍号 0–14、40–62、80–110 |
| 时长 | 基准 112 拍约 61 秒；结束还需全部敌人退场，实际可能更长；HP 归零提前失败 |
| 经济 | 正常击杀 +1 币；准备期回收 8 币，开战后回收 6 币 |
| 目标旋律 | do–mi–sol–do′；可夹杂其他音，目标音必须在不同拍依序出现，相邻目标音间隔 ≤4 拍 |
| 乐句奖励 | 最佳目标前缀长度为 0–4 层，每层 +1 币；≥2 层回复 1 HP，最多 10 HP |
| 终止式 | 完整旋律清除场上 1/4 敌人，向上取整；计入击杀数，但不记谱、不额外给击杀币 |
| 和声 | 同拍至少两次正常击杀记为一次和声，不能把同拍和弦当作连续旋律 |
| 得分 | 四舍五入(600×击杀率 + 300×剩余 HP 比例 + 900×已结算乐句完成度均值 + 60×和声次数) |
| 星级 | 击杀率 ≥90%、HP ≥8、完整旋律 ≥2 次，各奖励一星 |

暂停期间不能建造或修改塔。失去窗口焦点自动暂停。回放来自本局音符日志，保留同拍和声及中间停顿；日志只保存在当前运行实例中，没有保存或导出功能。

## 3. 程序结构

| 文件 | 职责 |
| --- | --- |
| `Assets/PianoDefense/Runtime/DefenseSimulation.cs` | 纯 C# 战斗状态、波次、布塔、移动、筛选、奖励、计分及快照 |
| `Assets/PianoDefense/Runtime/MelodyMatcher.cs` | 乐句最佳前缀匹配，同拍隔离及最大间隔约束 |
| `Assets/PianoDefense/Runtime/BeatClock.cs` | 80ms 提前调度、暂停恢复、卡顿后重新定位时钟 |
| `Assets/PianoDefense/Runtime/PianoSynthesis.cs` | C4–C5 八个自然音的带泛音衰减合成音 |
| `Assets/PianoDefense/Runtime/PianoAudio.cs` | 48 个 AudioSource 的复音池、DSP 预排程、试听、静音和节拍器 |
| `Assets/PianoDefense/Runtime/PianoDefenseGame.cs` | 游戏生命周期、待呈现拍、输入队列、音画衔接、回放 |
| `Assets/PianoDefense/Runtime/PianoDefenseView.cs` | IMGUI 中文界面、棋盘、塔配置、钢琴键、暂停与结算界面 |
| `Assets/PianoDefense/Editor/PianoDefenseBuilder.cs` | 场景生成、打开原型、Windows 64 位构建 |
| `Assets/PianoDefense/Editor/PianoDefenseChecks.cs` | 三项 Unity 控制器输入排队检查 |
| `Tests/PianoDefense.CoreTests/` | 独立 .NET 核心规则测试 |

音画流程：提前计算下一拍 → 用 `PlayScheduled` 安排音频 → 到 DSP 时间才更新画面快照 → 执行等待中的玩家指令。这个分层减少了画面提前显示未来状态，以及改塔影响已安排音符的问题。

界面按 1440×900 基准等比缩放。主要视觉元素、字体与音频在运行时生成，当前资产规模很小；本次资源清单中只有一个主场景，没有独立美术、采样音频或 Prefab 内容管线。

## 4. 已实现与规划的界线

**已实现**：单夜三波、钢琴塔、普通与装饰音怪、音高筛选、16 拍乐句匹配、分层奖励、终止式、结算评分、试听和完整日志回放。

**未实现**：白天采风、三夜进程、曲调库与选曲、多乐器、和弦怪/音痴怪/休止符怪、Boss、祝福三选一装配、金谱、商店、自由编谱、分享导出、移动端完整适配。

分层奖励属于当前原型的简化方案：原始系统设计文档中的延音包含“每层回血与建造折扣”，当前代码则是“每层给币、两层以上回 1 HP”，尚未等价实现原设计。原始评分中的消音、污染与结算币兑换也尚未实现。

历史分析文档中的优化前“39 个敌人”和“只有完整旋律获奖”已过时；当前为 44 个敌人与分层奖励。阅读这些文档时应区分优化前后描述。

## 6. 主要问题与下一步

1. **先补齐运行验证**：统一编辑器版本；准备 .NET 8 测试环境并恢复依赖访问；重跑 25 项测试、编辑器控制器检查和一轮实际试玩，再生成 Windows 包。
2. **验证双目标冲突是否成立**：当前示例布局的历史结果仍是满血全杀。它适合作为教学布局，但不能证明玩家需要在防守效率与旋律顺序之间取舍。记录玩家使用滤镜的频率、漏怪原因、乐句完成率和再次试玩意愿。
3. **先改善规则可读性**：游戏内解释同拍不算连续旋律、间隔 ≤4 拍和装饰音偶数列；明确波次考题和漏怪原因。现有一般提示和快怪标记是基础，仍需实玩确认理解成本。
4. **核对波间节奏**：当前普通出生事件在 14→40、62→80 之间有空档，但仍有敌人在行进，不能直接把原设计的“8 拍间奏”当作当前实际整备时长。若需要真正整备阶段，应显式实现阶段与相应操作规则。
5. **再扩展内容**：先把波次和曲调从硬编码变成配置，再选一个具有策略意义的组合，例如鼓塔与音痴怪。多乐器需要扩展音符日志的音色字段，HP 型敌人需要攻击伤害与存活状态。
6. **提升表现与交付稳定性**：击杀音符反馈和终止式演出优先于大量新增系统；采样音源、跨平台中文字体与触屏输入应随目标平台验证。当前复音音量衰减有助于控制叠加，但没有实测证据证明所有密集和声均无削波。

总体判断：核心系统结构清晰，单夜闭环已经成型；当前最有价值的推进是恢复可靠验证、确认“防守成曲”的可听性和策略性，再有选择地扩展内容。
